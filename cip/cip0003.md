## Summary

Move pods’ “named dataset → download into cache → load” path onto
lynguine’s config-driven **materialise then read** seam
([lynguine CIP-0009](https://github.com/lawrennd/lynguine/blob/main/cip/cip0009.md),
[lynguine#20](https://github.com/lawrennd/lynguine/issues/20)), without
pretending that a single `remote.type: url` replaces the pods catalogue.

The demonstrator (and the intended production shape) is **two-stage**:

1. **Materialise the data-resources catalogue** (`data_resources.json` /
   `.yml`) with ordinary `remote.type: url` (or `github`).
2. **Use that local catalogue** to resolve a named dataset and materialise
   its `urls` + `files` (and optional `dirs` / `suffices`) into the cache,
   then read with a local `type:` (CSV first; other readers later).

Pods keeps thin `pods.datasets.*` loaders and teaching APIs where useful;
download/authorise/cache become lynguine access-stage work.

## Motivation

Today pods embeds `pods/data_resources.json` in the package and downloads
with its own `access.download_data` / `download_url` stack. lynguine already
has overlapping helpers (`FileDownloader` still speaks a
`data_resources[name]` dict) and is gaining an explicit `remote:` hook in
`from_flow` (CIP-0009). Leaving two download stacks drifts licence prompts,
cache layout, and path confinement (lynguine CIP-000A).

A naïve “one URL in the interface YAML” demo under-sells pods: the catalogue
*is* the product surface (citation, licence, multi-file bundles, mirror vs
original URLs). Fetching the catalogue first, then expanding a named entry,
keeps that surface honest and shows why CIP-0009 is the right prerequisite
rather than a complete pods replacement by itself.

## Detailed Description

### What stays in pods vs what moves to lynguine

| Concern | Owner after this CIP |
|---------|----------------------|
| Catalogue schema (`urls`, `files`, `dirs`, `suffices`, citation, licence, size) | pods (file format); lynguine learns to *consume* it |
| Fetch catalogue bytes | lynguine `remote:` (url/github) |
| Expand named entry → one or more file fetches + licence prompt | lynguine `remote.type: data_resources` (or ods-registered remote type) |
| Cache root / path jail | lynguine (CIP-000A) |
| `pods.datasets.bmi_steps()` etc. | pods — thin wrappers over materialised paths / frames |
| Teaching notebooks / GPSS | unchanged call sites where possible |

### Two-stage flow (demo and default mental model)

**Stage A — catalogue on disk**

```yaml
cache:
  type: json
  filename: data_resources.json
  directory: .lynguine-cache/pods-catalogue
  remote:
    type: url
    url: https://raw.githubusercontent.com/lawrennd/ods/main/pods/data_resources.json
```

**Stage B — named dataset from that catalogue**

```yaml
input:
  type: csv
  filename: steps-bmi-data.csv
  directory: .lynguine-cache/bmi_steps
  index: null
  remote:
    type: data_resources
    catalogue: .lynguine-cache/pods-catalogue/data_resources.json
    name: bmi_steps
    # refresh: true   # optional; refresh files and/or re-read catalogue policy TBD
```

Semantics for `remote.type: data_resources`:

1. Require a local `catalogue` path (JSON object keyed by dataset name, as
   today’s `data_resources.json`). Do **not** silently ship a package-embedded
   catalogue in the demo path — the point is that stage A already ran.
2. Look up `name`. Fail loudly if missing.
3. Reuse pods’ zip of `urls` × `files` (and `dirs` / `suffices` when present):
   each file is `urljoin(url, [dir,] filename)` into
   `directory` / dataset layout compatible with today’s `DATAPATH` /
   `store_directory` behaviour where practical.
4. Honour citation / licence / size messaging via the existing authorize
   path (CIP-0009 `authorize_remote` / pods prompt text).
5. Skip files already present unless `refresh: true`.
6. Then the ordinary local `type: csv` (demo) reads `filename`.

Optional sugar (later, not required for the demo): a single remote block with
`catalogue_url` + `name` that performs A then B. The **documented demo keeps
A and B separate** so operators see the catalogue as a first-class artefact.

### Relation to lynguine#20 / CIP-0009

| On lynguine#20 | On this CIP |
|----------------|-------------|
| Close when CIP-0009 materialise url/github lands | Depends on that hook |
| Thin url→file example | **Catalogue→named dataset** example (`bmi_steps`) |
| Nested `remote:` under hstack (follow-on) | Multi-file *sidecar* bundles via catalogue expansion, not via hstack |
| Live readers (CIP-0019) | Out of scope |

Do **not** close lynguine#20 by completing this CIP. Link both ways: #20 is
the prerequisite seam; this CIP is the pods product cutover and the
catalogue-driven demonstration.

### Multi-file and exotic loaders

- **Fetch many, read one** (e.g. `housing.data` + `housing.names`): stage B
  materialises the whole entry; the reader / `pods.datasets.*` picks the
  file(s) it needs. That is catalogue expansion, not `hstack`.
- **Fetch many, join as tables**: compose CIP-0009 nested `remote:` children
  once that wiring exists — orthogonal.
- **`.mat` / HDF5 / custom**: remain pods (or later lynguine `type:` plugins).
  Stage B only guarantees bytes on disk.

### Phasing

1. **Demo** — stage A + B for `bmi_steps` (single CSV); documented under
   lynguine `examples/` and/or ods notebooks; comment on lynguine#20.
2. **Hook** — implement `remote.type: data_resources` in lynguine (or register
   from ods via a small remote-type registry mirroring CIP-0019).
3. **Compatibility** — `pods.access.download_data` delegates to the hook when
   lynguine is available; keep fallback during transition.
4. **Cutover** — more datasets; stop maintaining a parallel download stack;
   catalogue may live on the mirror repo URL instead of only in the wheel.

## Implementation Plan

1. **Agree interface** — `remote.type: data_resources` fields (`catalogue`,
   `name`, `refresh`); confirm JSON keying matches `data_resources.json`.
2. **Lynguine hook** — implement expansion + authorize + cache skip; tests
   with a tiny fixture catalogue (no live network in CI).
3. **Demo** — interface YAML (or notebook) that materialises the real
   catalogue URL then `bmi_steps`; link from lynguine#20 and CIP-0009.
4. **Pods bridge** — optional thin wrapper so `pods.datasets.bmi_steps()`
   uses the materialised cache path.
5. **Migration backlog** — per-dataset or per-family tasks after Accept.

## Backward Compatibility

- Existing `pip install pods` + `pods.datasets.*` keep working during
  transition (delegation or dual path).
- Catalogue schema unchanged initially (JSON keyed by name).
- YAML list form (`datasets: [...]`) may need a normaliser if we prefer YAML
  on the wire; JSON remains the demo source of truth.

## Testing Strategy

- Unit: expand fixture catalogue; cache skip; missing name; dirs/suffices;
  licence deny.
- Integration: mocked HTTP for catalogue + CSV; then `from_flow` read.
- Optional smoke (manual / periodic): live `bmi_steps` against
  `datasets_mirror`.
