## Summary

Replace Poetry with [uv](https://docs.astral.sh/uv/) as the project’s
dependency manager, lockfile tool, and local/CI install path for `pods`
(this repository: `ods`).

End state: PEP 621 metadata in `pyproject.toml`, a `uv.lock` lockfile, CI
and publish workflows that use `uv`, and contributor docs that no longer
mention Poetry. PyPI consumers who `pip install pods` are unaffected.

## Motivation

The project still uses Poetry end-to-end:

- `pyproject.toml` is `[tool.poetry]` with `poetry-core` as build backend
- `poetry.lock` is the lockfile
- GitHub Actions (`tests.yml`, `publish.yml`, `release.yml`) install via
  `snok/install-poetry` and run `poetry install` / `poetry run` /
  `poetry build` / `poetry publish`
- `docs/publishing.md` documents Poetry for manual releases

Poetry remains workable, but it has already collided with the toolchain:
the backlog item to drop Python 3.9 was driven by Poetry 2.5.x requiring
Python ≥3.10 while CI still tested 3.9. That pattern — packaging tool
constraints shaping the supported Python matrix — is a recurring tax.

uv gives a single fast tool for create/sync/lock/build/publish, speaks
standard PEP 621 / optional-dependencies / dependency-groups, and matches
the direction of related projects in this ecosystem. Migrating now
clears Poetry-specific CI friction before further packaging or test
infrastructure work (CIP-0001) piles more Poetry assumptions into
workflows.

## Detailed Description

### Scope

| In scope | Out of scope |
|----------|--------------|
| Convert `pyproject.toml` to PEP 621 + uv-compatible layout | Changing runtime API of `pods` |
| Replace `poetry.lock` with `uv.lock` | Renaming the PyPI package (`pods`) |
| Rework GitHub Actions to use uv | Migrating other repos in the ecosystem (unless they share workflows) |
| Update contributor/publish docs | Redesigning extras beyond faithful translation |
| Keep Python `>=3.10` and existing extras | Dropping or adding Python versions (separate decision) |

### Target `pyproject.toml` shape

Move from Poetry tables to standards-based metadata:

1. **`[project]`** (PEP 621) — name, version, description, authors, license,
   requires-python, dependencies, classifiers, urls, scripts if any.
2. **`[project.optional-dependencies]`** — faithful map of current
   `[tool.poetry.extras]` (`hdf5-compatibility`, `google-trends-interface`,
   `all-datasets`, etc.).
3. **`[dependency-groups]`** (PEP 735) — current
   `[tool.poetry.group.dev.dependencies]` (pytest, twine, optional dataset
   libs used in tests, etc.). Prefer dependency groups over inventing a
   Poetry-style `dev` extra unless we deliberately want `pip install
   pods[dev]`.
4. **`[build-system]`** — use a PEP 517 backend that uv supports well
   (recommended default: `hatchling`). Drop `poetry-core`.
5. **Package data** — preserve inclusion of `pods/defaults.cfg`,
   `pods/data_resources.json`, and `pods/football_teams.json` via the
   chosen backend’s package-data config (e.g. hatch `[tool.hatch.build.targets.wheel]`
   / force-include), verified by inspecting the built wheel.
6. **Tool config** — keep `[tool.pytest.ini_options]`; remove
   `[tool.poetry*]` once unused.

Version bump workflow today edits `[tool.poetry] version`. After migration,
version lives in `[project] version` (or a single hatch version source —
pick one and document it in `docs/publishing.md`).

### Lockfile and local workflow

| Today (Poetry) | After (uv) |
|----------------|------------|
| `poetry install --with dev` | `uv sync --all-extras` or `uv sync --group dev` (+ extras as needed) |
| `poetry run pytest` | `uv run pytest` |
| `poetry lock` | `uv lock` |
| `poetry build` | `uv build` |
| `poetry publish` | `uv publish` (preferred; no twine) |
| `poetry.lock` committed | `uv.lock` committed; delete `poetry.lock` |

CI should install extras needed for the test suite (today’s gap noted in
backlog “Fix Missing Dependencies”: prefer
`uv sync --group dev --all-extras` or an explicit `all-datasets` extra so
dataset tests get their optional deps). Align with CIP-0001 rather than
leaving CI under-installed.

### GitHub Actions

Replace Poetry install steps in:

- `.github/workflows/tests.yml`
- `.github/workflows/publish.yml`
- `.github/workflows/release.yml`

Recommended pattern:

1. `actions/checkout`
2. `astral-sh/setup-uv` (pin a major or use their documented caching)
3. `uv python pin` / setup-python only if we still need an explicit matrix
   interpreter; otherwise let uv manage the matrix Python version
4. `uv sync --frozen` (or equivalent) with the same extras/groups as local
5. `uv run pytest …`
6. For publish: `uv build` then **`uv publish`** (not twine)

**Publishing auth (no new secret required if current setup works):**

- Current `publish.yml` already has `permissions.id-token: write`,
  `environment: release`, and `secrets.PYPI_API_TOKEN` for Poetry.
- **Preferred:** Trusted Publishing (OIDC). Configure PyPI’s trusted
  publisher for owner `lawrennd`, repo `ods`, workflow `publish.yml`,
  environment `release`, then run bare `uv publish` in CI. No API token
  secret is needed for that path.
- **Fallback:** Keep using the existing repo secret `PYPI_API_TOKEN` as
  `UV_PUBLISH_TOKEN` (or `uv publish --token`), with
  `--trusted-publishing never` if OIDC is not registered on PyPI.
- Do **not** create a differently named secret unless rotating credentials;
  reuse `PYPI_API_TOKEN` or drop it once trusted publishing is verified.
- Drop `twine` from the default publish path and from required CI deps
  once `uv publish` is in place.

Version-check steps that call `poetry version -s` must read
`[project].version` instead (e.g. `uv version` / parse `pyproject.toml`).

### Documentation

Update at least:

- `docs/publishing.md` — all Poetry commands → uv; version field path
- Any README or contributor notes that mention Poetry
- Backlog items that prescribe `poetry install …` (amend notes when this
  CIP is implemented, or leave a one-line pointer)

### Alternatives considered

1. **Stay on Poetry** — lowest immediate effort; keeps CI/docs as-is; does
   not remove Poetry/Python coupling or align with uv-first workflows.
2. **PEP 621 + pip-tools / plain pip** — standards-friendly but slower and
   more fragmented than uv for lock + sync + build + publish.
3. **PDM / Hatch as primary CLI** — Hatch is a fine *build* backend; uv as
   the day-to-day CLI covers install/lock/CI with less tool sprawl.

**Decision (proposed):** uv CLI + hatchling build backend + PEP 621
metadata + committed `uv.lock`.

### Risks

- **Wheel contents** — package data files must still ship; verify with
  `uv build` and inspect the wheel before the first post-migration release.
- **Extras vs dependency-groups** — PyPI extras must remain installable via
  `pip install pods[all-datasets]`; do not bury those only in private
  dependency groups.
- **Release automation** — publish/release workflows are Poetry-shaped;
  migrate and dry-run on TestPyPI or a dry-run job before cutting a real
  release.
- **Publish auth** — if PyPI trusted publisher is not yet registered for
  this workflow/environment, the first `uv publish` OIDC attempt will
  fail until that is set; keep `PYPI_API_TOKEN` as fallback until then.
- **Contributor muscle memory** — document the short command map in
  publishing docs.

## Implementation Plan

1. **Inventory**
   - List all Poetry touchpoints (pyproject, lockfile, workflows, docs,
     backlog snippets).
   - Confirm extras → optional-dependencies mapping 1:1.

2. **Convert `pyproject.toml`**
   - Write PEP 621 `[project]` and optional-dependencies.
   - Move dev deps to `[dependency-groups]`.
   - Switch build-system to hatchling; configure package data.
   - Remove `[tool.poetry*]` tables.

3. **Lock and verify locally**
   - `uv lock` → commit `uv.lock`.
   - Remove `poetry.lock`.
   - `uv sync` + `uv run pytest` (with extras as needed).
   - `uv build` and confirm packaged JSON/CFG files are present.

4. **CI / release workflows**
   - Rewrite tests, publish, and release workflows for uv.
   - Publish job: `uv build` + `uv publish` (trusted publishing preferred;
     else `UV_PUBLISH_TOKEN` from existing `PYPI_API_TOKEN`).
   - Ensure matrix still covers 3.10–3.12 (current support).
   - Replace `poetry version` checks with project-version reads.

5. **Docs**
   - Update `docs/publishing.md` and any contributor-facing Poetry
     references (including `uv publish` auth notes).

6. **Validation cut**
   - Green CI on the migration PR.
   - Confirm PyPI trusted publisher matches workflow + `release`
     environment, or that `PYPI_API_TOKEN` remains set.
   - Optional: TestPyPI publish dry-run before the next real release.

## Backward Compatibility

- **PyPI / end users**: `pip install pods` and `pip install pods[extra]`
  remain the supported consumer path. No runtime API change.
- **Contributors**: must install uv and use `uv sync` / `uv run` instead of
  Poetry. Document clearly.
- **Version tags / release process**: same GitHub Release → Actions → PyPI
  shape; only the tool underneath changes.
- **Lockfile**: `poetry.lock` removed; clones need uv to reproduce the
  locked env.

## Testing Strategy

- Local: `uv sync` (dev + extras), full pytest, wheel content check.
- CI: same matrix as today (3.10, 3.11, 3.12); coverage upload unchanged in
  intent.
- Publish path: workflow syntax check + dry-run build; prefer TestPyPI
  before the first production publish after migration.
- Regression: confirm optional extras still resolve for dataset tests that
  need them (ties to CIP-0001 / missing-deps backlog).
